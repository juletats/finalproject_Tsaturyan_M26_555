# finalproject_Tsaturyan_M26_555

Итоговый проект. Платформа для отслеживания и симуляции торговли валютами.

## 1. Подготовка

### Обзор проекта

**Valuta Trade Hub** - консольное приложение, платформа для отслеживания и симуляции
торговли валютами. Пользователь регистрируется, ведёт портфель кошельков в фиатных и
крипто-валютах, покупает и продаёт валюту по актуальным курсам и получает сводку
стоимости портфеля в выбранной базовой валюте. Данные хранятся в JSON-файлах,
курсы - в локальном кеше `data/rates.json`, который наполняет отдельный
Parser Service. Валюты описаны иерархией классов (`Currency` → `FiatCurrency` /
`CryptoCurrency`) с единым реестром, конфигурация собрана в одном `SettingsLoader`,
доступ к файлам - в одном `DatabaseManager`, а ключевые операции пишутся в журнал
`logs/actions.log` (журнал парсера ведётся отдельно - в `logs/parser.log`).

Платформа рассчитана на два сервиса:

* **Core Service** - это приложение: CLI, пользователи, портфели, сделки,
  история операций, работа с курсами.
* **Parser Service** - отдельное приложение-парсер (`valutatrade_hub/parser_service/`),
  которое получает курсы из CoinGecko и ExchangeRate-API, пишет историю замеров
  в `data/exchange_rates.json` и обновляет `data/rates.json`. Запускается
  из CLI командой `update-rates` (однократно или фоном по `--interval`).
  Подробности - в пункте 4.

Core читает только кеш курсов и никогда не обращается в API сам: внешнего
HTTP-запроса нет в бизнес-логике, а у кеша есть срок годности - просроченные
данные дают явную ошибку `StaleRatesError` с предложением выполнить
`update-rates` (см. раздел 4.7).

Слои зависят друг от друга только в одну сторону: `cli` разбирает строку и
печатает, вызывая `core.usecases`; бизнес-логика (`core/usecases.py`) работает с
моделями (`core/models.py`), реестром валют (`core/currencies.py`), чистыми
функциями (`core/utils.py`) и хранилищем (`infra/database.py`); тексты ошибок
сосредоточены в `core/exceptions.py`; пути, TTL курсов и параметры логов - в
`infra/settings.py`. `decorators.py` импортирует только `logging_config` и
`utils`, поэтому циклических импортов между слоями нет (имя пользователя для
строки лога приходит через резолвер, который регистрирует `usecases`).

`parser_service` - соседний слой, а не часть бизнес-логики: Core его не
импортирует. Парсер зависит только от `core/utils.py`, `core/exceptions.py`,
`infra/settings.py`, `infra/database.py` и `logging_config.py`, а связывает их
CLI: `update-rates` запускает парсер, а `get-rate`/`buy`/`show-portfolio` читают
уже записанный кеш.

Переменная `VALUTATRADE_HOME` задаёт корень запуска: внутри оказываются
и `data/`, и `logs/` - одним переключением можно изолировать весь запуск.
Уровень логов переопределяется переменной `VALUTATRADE_LOG_LEVEL` (например,
`DEBUG`), интервал фонового обновления - переменной
`VALUTATRADE_PARSER_INTERVAL` (секунды). Ключ ExchangeRate-API приходит только
из переменной окружения `EXCHANGERATE_API_KEY` и в коде не хранится (раздел 4.3).
Все параметры перечислены в секции `[tool.valutatrade]` файла
`pyproject.toml`, необязательный `config.json` в корне проекта перекрывает их,
а переменные окружения - перекрывают `config.json`.

## 2.1. Модели предметной области

Состояние моделей защищено: атрибуты приватны (`_balance`, `_wallets`,
`_hashed_password`), наружу отдаются через геттеры, а изменяемые поля - через
сеттеры с проверкой инвариантов. Доменные исключения вынесены в
`core/exceptions.py`, поэтому тексты сообщений не дублируются между слоями.

### `User` - пользователь системы

Приватные атрибуты: `_user_id`, `_username`, `_hashed_password`, `_salt`,
`_registration_date`. Пароль нигде не хранится в открытом виде: используется
односторонний псевдо-хеш `sha256(password + salt)`, соль случайна и хранится
рядом.

| Элемент                                                   | Назначение                                           |
|-----------------------------------------------------------|------------------------------------------------------|
| `User.create(username, password, user_id)`                | создаёт пользователя с новой солью и хешем           |
| `get_user_info()`                                         | строка с id, именем и датой регистрации (без пароля) |
| `change_password(new_password)`                           | проверяет длину, перегенерирует соль и хеш           |
| `verify_password(password)`                               | сверяет введённый пароль с сохранённым хешем         |
| `user_id`, `registration_date`, `hashed_password`, `salt` | геттеры без setters                                  |
| `username`                                                | геттер + сеттер: имя не может быть пустым            |
| `to_dict()` / `from_dict()`                               | запись для `users.json`                              |

### `Wallet` - кошелёк одной валюты

Приватные атрибуты: `_currency_code`, `_balance`, `_currency` (кеш объекта
валюты из реестра - точка интеграции модели с `core/currencies.py`).

| Элемент              | Назначение                                                               |
|----------------------|--------------------------------------------------------------------------|
| `balance` (property) | геттер; сеттер отклоняет отрицательные значения и нечисловые данные      |
| `deposit(amount)`    | пополнение, `amount` обязано быть положительным числом                   |
| `withdraw(amount)`   | снятие с проверкой остатка, иначе `InsufficientFundsError`               |
| `get_balance_info()` | строка вида `BTC: 0.0500`                                                |
| `currency_code`      | геттер без setters, код приводится к верхнему регистру                   |
| `currency`           | геттер объекта `Currency` из реестра; для кода вне реестра - `None`      |
| `get_display_info()` | данные реестра плюс баланс: `[CRYPTO] BTC - Bitcoin (...) / BTC: 0.0500` |

### `Portfolio` - все кошельки одного пользователя

Приватные атрибуты: `_user_id`, `_wallets`, `_user`.

| Элемент                                    | Назначение                                                                             |
|--------------------------------------------|----------------------------------------------------------------------------------------|
| `add_currency(currency_code, balance=0.0)` | создаёт кошелёк; код валюты обязан быть уникальным                                     |
| `get_wallet(currency_code)`                | возвращает кошелёк или `WalletNotFoundError`                                           |
| `get_total_value(base_currency='USD')`     | суммарная стоимость портфеля в базовой валюте по курсам                                |
| `user`                                     | геттер объекта пользователя, перезапись запрещена (`bind_user` привязывает однократно) |
| `wallets`                                  | геттер возвращает копию словаря, состояние в обход методов не меняется                 |

## 2.2. Командный интерфейс

CLI живёт в `valutatrade_hub/cli/interface.py` и является единственной точкой
входа пользовательских команд: строка разбирается `shlex`, аргументы проверяются,
вызывается бизнес-логика из `core/usecases.py`, результат печатается.

| Команда          | Аргументы                           | Результат                                           |
|------------------|-------------------------------------|-----------------------------------------------------|
| `register`       | `--username <str> --password <str>` | пользователь в `users.json` + пустой портфель       |
| `login`          | `--username <str> --password <str>` | сессия текущего запуска                             |
| `show-portfolio` | `[--base <str>]`                    | кошельки и итог в базовой валюте (по умолчанию USD) |
| `buy`            | `--currency <str> --amount <float>` | кошелёк создаётся автоматически, баланс пополняется |
| `sell`           | `--currency <str> --amount <float>` | баланс списывается                                  |
| `get-rate`       | `--from <str> --to <str>`           | курс пары и обратный курс с меткой времени          |
| `update-rates`   | `[--source <str>] [--interval <int>]` | запустить парсер: однократно или фоном (раздел 4.6)  |
| `show-rates`     | `[--currency <str>] [--top <int>] [--base <str>]` | курсы из локального кеша с фильтрами  |
| `stop-parser`    | -                                   | остановить фоновое обновление курсов                |
| `help`, `exit`   | -                                   | справка, выход                                      |

Пример сессии:

```text
Изменения в портфеле:

Портфель пользователя 'me' (база: USD):
- BTC: 0.0500  → 2966.86 USD

---------------------------------
```

```text

Неизвестная валюта 'XYZ'
Поддерживаемые валюты: BTC, ETH, EUR, GBP, RUB, SOL, TRY, USD. Справка: help get-rate
>>> get-rate --from USD --to GBP

>>> get-rate --from BTC --to USD
Курсы устарели: обновлено 2026-11-08 03:00:00, срок годности 300 с. Выполните update-rates.
Срок годности кеша задаёт настройка rates_ttl_seconds (сейчас 300 с).
```

Ошибки самого парсера (429, неверный ключ, недоступный эндпоинт) не
превращаются в исключение для пользователя: `update-rates` печатает строку
`ERROR:` по каждому источнику и продолжает работу с остальными - раздел 4.6,
полный разбор - в `logs/parser.log`.

Пара `USD→GBP` из примера выше - это не «такой валюты не существует», а «курса
нет в кеше»: GBP есть в реестре валют, но котировку не отдаст пропущенный без
ключа API источник ExchangeRate-API. Неизвестный код (`XYZ`) даёт
`CurrencyNotFoundError` с перечислением справочника - две ветки намеренно
различаются.

Дополнительно: сессия живёт в рамках одного запуска, поэтому многошаговые
сценарии (`login` → `buy` → `show-portfolio`) выполняются в интерактивном режиме (`make run`); режим одной команды
удобен для запроса курсов. Покупка и продажа
считаются «оценочно» - USD-кошелёк в сделках не участвует; чтобы включить
расчёты через него, в `usecases.py` нужно поставить `SETTLE_IN_USD = True`.

### Форматы данных

`data/users.json` - массив записей пользователя:

```json
[
  {
    "user_id": 1,
    "username": "me",
    "hashed_password": "9f86d081...",
    "salt": "d3Bx9K",
    "registration_date": "2026-11-08T16:54:06"
  }
]
```

`data/portfolios.json` - массив портфелей, кошельки ключуются кодом валюты:

```json
[
  {
    "user_id": 1,
    "wallets": {
      "USD": {
        "balance": 1500.0
      },
      "BTC": {
        "balance": 0.05
      }
    }
  }
]
```

`data/rates.json` - снимок курсов, который читает Core: пары вида `EUR_USD`
(сколько USD стоит 1 EUR), для каждой пары `rate`, `updated_at` и `source`, плюс
`last_refresh` для всей таблицы. Полный формат и правила - в разделе 4.4.
Курс считается актуальным `rates_ttl_seconds = 300` секунд (настройка из
конфигурации, читается динамически); просроченный кеш автоматически не
обновляется - Core отвечает ошибкой `StaleRatesError`. Курсов без данных в кеше
нет и в `get-rate` они дают `RateLookupError`. Пары, которых нет в кеше
напрямую (например, `EUR→BTC`), вычисляются через базовую валюту.

## 3. Усложнение и гибкость модели данных

Три новых сущности делают модель расширяемой: иерархия валют вместо
строк-кодов, единые доменные исключения вместо разрозненных текстов, синглтоны
конфигурации, хранилища, журнал операций, который ведёт декоратор.

### 3.1. Иерархия валют (`core/currencies.py`)

Валюта больше не строка-код: справочник описан классами с общим интерфейсом, и
любой объект умеет сам себя представить для UI и логов.

| Элемент                | Назначение                                                                                    |
|------------------------|-----------------------------------------------------------------------------------------------|
| `Currency(name, code)` | абстрактный базовый класс (`ABC`): публичные атрибуты и требование к описанию, без реализации |
| `get_display_info()`   | абстрактный метод - строковое представление валюты                                            |
| `kind`                 | метка типа по имени класса: `FIAT` или `CRYPTO`                                               |
| `__str__`              | возвращает `get_display_info()`, поэтому валюта печатается «как в справочнике»                |
| `FiatCurrency`         | добавляет `issuing_country` (страна или зона эмиссии)                                         |
| `CryptoCurrency`       | добавляет `algorithm` и `market_cap` (последняя известная капитализация; `0.0` - данных нет)  |

Инварианты проверяются в `__post_init__` и дают `ValidationError`:

* `code` - 2-5 символов в верхнем регистре без пробелов (тот же
  `utils.validate_currency_code`, что и для кошельков); регистр ввода не значим:
  `get_currency("btc")` возвращает `BTC`;
* `name` - непустая строка;
* у фиата обязана быть страна эмиссии, у крипты - алгоритм; капитализация -
  неотрицательное число.

Формат строк, который показывает приложение:

```text
[FIAT] USD - US Dollar (Issuing: United States)
[CRYPTO] BTC - Bitcoin (Algo: SHA-256, MCAP: 1.12e12)
```

Реестр - словарь экземпляров плюс фабрика:

| Элемент                                                     | Назначение                                                                           |
|-------------------------------------------------------------|--------------------------------------------------------------------------------------|
| `get_currency(code)`                                        | валюта по коду; для неизвестного кода - `CurrencyNotFoundError`                      |
| `find_currency(code)`                                       | то же, но `None` вместо исключения - используется моделями, где валюта факультативна |
| `supported_codes()`                                         | коды справочника; их печатает CLI в подсказке к ошибке                               |
| `FIAT_CURRENCIES`, `CRYPTO_CURRENCIES`, `CURRENCY_REGISTRY` | данные справочника: USD, EUR, GBP, RUB, TRY, BTC, ETH, SOL                                |

GBP и SOL добавлены вместе с Parser Service: это те валюты, чьи котировки
приходят из внешнего API (GBP - ExchangeRate-API, SOL - CoinGecko по ID
`solana`). Заглушка, которой наполняется пустой кеш при первом запуске, знает
те же коды, поэтому TRY и GBP наглядно показывают и ветку успеха, и ветку
`RateLookupError`, если пары в кеше нет.

### 3.2. Исключения (`core/exceptions.py`)

Все доменные ошибки - потомки `ValutaTradeError(ValueError)`, поэтому CLI
перехватывает их одним блоком; каждая несёт финальный текст сообщения.

| Исключение                                                                                                                        | Сообщение                                                                        | Где возникает                                                          | Реакция CLI                                     |
|-----------------------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------|------------------------------------------------------------------------|-------------------------------------------------|
| `InsufficientFundsError`                                                                                                          | `Недостаточно средств: доступно {available} {code}, требуется {required} {code}` | `Wallet.withdraw()`, через него - `usecases.sell()`                    | текст как есть                                  |
| `CurrencyNotFoundError`                                                                                                           | `Неизвестная валюта '{code}'`                                                    | `currencies.get_currency()`, валидация кодов в `buy`/`sell`/`get-rate` | текст + список кодов + `Справка: help get-rate` |
| `ApiRequestError`                                                                                                                 | `Ошибка при обращении к внешнему API: {reason}`                                  | слой получения курсов: `parser_service/api_clients.py` (сети, 4xx, битый JSON, чужая база) | текст + подсказка про повтор и сеть             |
| `StaleRatesError`                                                                                                                 | `Курсы устарели: обновлено {момент}, срок годности {ttl} с. Выполните update-rates.` | `usecases.fresh_rates()` / `lookup_rate()` при кеше старше TTL                             | текст + строка про `rates_ttl_seconds`          |
| `RateLookupError`                                                                                                                 | `Не удалось получить курс для {from}→{to}`                                       | `usecases.price_to_base()` при сделке без котировки                    | текст как есть                                  |
| `UnknownCurrencyError`                                                                                                            | `Неизвестная базовая валюта '{code}'`                                            | `show-portfolio --base`                                                | текст как есть                                  |
| `ValidationError`                                                                                                                 | текст проверщика (код, имя, сумма, пароль)                                       | валидаторы `utils` и модели                                            | текст как есть                                  |
| `WalletNotFoundError`, `WalletExistsError`, `DuplicateUsernameError`, `UserNotFoundError`, `WrongPasswordError`, `NoSessionError` | см. таблицу ошибок раздела 2.2                                                   | модели и `usecases`                                                    | текст как есть                                  |

Исключение никогда не глотается: декоратор логирует факт ошибки и пробрасывает
её дальше, а портфель не сохраняется, если сделка не состоялась.

### 3.3. Singleton: конфигурация и хранилище (`infra/`)

Оба синглтона построены на метаклассе `Singleton` (`infra/__init__.py`).
Метакласс выбран вместо `__new__`, потому что перехватывает сам вызов класса:
экземпляр создаётся один раз и `__init__` не выполняется повторно при каждом
`SettingsLoader()`, поведение автоматически достаётся наследникам, а в коде
класс объявляется обычно: `class SettingsLoader(metaclass=Singleton)`.
Повторные импорты модулей новых экземпляров не создают.

`SettingsLoader` - единая точка конфигурации:

| Метод                   | Назначение                                                                                                   |
|-------------------------|--------------------------------------------------------------------------------------------------------------|
| `get(key, default=...)` | значение настройки; без `default` и при опечатке в ключе - `KeyError`, чтобы ошибка не превращалась в `None` |
| `reload()`              | перечитать все источники; экземпляр остаётся прежним                                                         |
| `as_dict()`             | копия значений - для отладки и логов                                                                         |

Источники по возрастанию приоритета: значения по умолчанию →
`pyproject.toml` (секция `[tool.valutatrade]`, читается стандартным `tomllib`) →
`config.json` в корне проекта → переменные окружения.

| Ключ                                          | Значение по умолчанию                         | Смысл                                       |
|-----------------------------------------------|-----------------------------------------------|---------------------------------------------|
| `data_dir`                                    | `./data`                                      | каталог JSON-хранилища                      |
| `users_file`, `portfolios_file`, `rates_file` | `users.json`, `portfolios.json`, `rates.json` | имена файлов коллекций                      |
| `exchange_rates_file`                         | `exchange_rates.json`                         | файл истории замеров парсера                |
| `rates_ttl_seconds`                           | `300`                                         | политика свежести кеша курсов               |
| `base_currency`                               | `USD`                                         | базовая валюта оценок и итогов              |
| `min_password_length`                         | `4`                                           | минимальная длина пароля                    |
| `log_dir`, `log_file`                         | `./logs`, `actions.log`                       | куда писать журнал                          |
| `parser_log_file`                             | `parser.log`                                  | отдельный журнал парсера                    |
| `log_level`                                   | `INFO`                                        | базовый уровень логов (`DEBUG` для отладки) |
| `log_format`                                  | `text`                                        | формат записей: `text` либо `json`          |
| `log_max_bytes`, `log_backup_count`           | `1000000`, `3`                                | ротация журнала                             |
| `parser_request_timeout`                      | `10`                                          | таймаут ожидания ответа API                 |
| `parser_update_interval_seconds`              | `900`                                         | период фонового обновления курсов           |
| `parser_history_limit`                        | `5000`                                        | сколько записей журнала хранить             |

Относительные пути разбираются от текущей директории, а
`VALUTATRADE_HOME` содержит  и `data/`, и `logs/`, 
`VALUTATRADE_LOG_LEVEL` - уровень логов, `VALUTATRADE_PARSER_INTERVAL` -
период обновления. Ключ API в настройки не входит: `EXCHANGERATE_API_KEY`
читается только из окружения и только в `parser_service/config.py`.

`DatabaseManager` - единая точка доступа к JSON-файлам: пути читаются из
`SettingsLoader` в момент обращения, поэтому `reload()` сразу меняет
расположение хранилища.

| Метод                           | Назначение                                                                                      |
|---------------------------------|-------------------------------------------------------------------------------------------------|
| `path(collection)`              | полный путь коллекции (`users`, `portfolios`, `rates`, `exchange_rates`)                        |
| `read(collection, default)`     | устойчивое чтение: битый или отсутствующий JSON даёт `default`, а не исключение                 |
| `write(collection, data)`       | атомарная запись: временный файл + `os.replace`, поэтому в хранилище не бывает обрезанного JSON |
| `update(collection, transform)` | безопасная операция чтение → изменение → запись                                                 |

Синглтоны используются здесь: `core/utils.py` (пути, `BASE_CURRENCY`,
`MIN_PASSWORD_LENGTH`, TTL), `core/usecases.py` (`DATABASE.read/write/update`
вместо прямой работы с файлами), `logging_config.py` (уровень, формат, ротация),
`decorators.py` (формат строки журнала).

### 3.4. Журнал операций (`logging_config.py`, `decorators.py`)

Формат зафиксирован: текстовая строка, где после уровня и времени идут поля
операции, - её проще читать глазами, и она совпадает с примером из задания.
Если включить настройку `log_format = "json"`, каждая строка становится
отдельным JSON-объектом с теми же полями. Логи пишутся только в файл (`propagate = False`), поэтому вывод CLI остаётся
прежним. Ротация - по размеру:
`logs/actions.log` до `log_max_bytes` байт и `log_backup_count` архивных копий (`actions.log.1`, `actions.log.2`, ...).
Базовый уровень - INFO, для отладки -
DEBUG. Посмотреть
журнал можно командой `make logs` (или `make logs LOG_LINES=50`).

Декоратор `@log_action(action, verbose=False)` берёт поля из аргументов вызова
через `inspect.signature`, поэтому список полей не зависит от порядка
позиционных аргументов. Поля: timestamp (ISO), `action`, `user` (или `user_id`),
`currency`, `amount`, `rate`, `base`, `result` (`OK`/`ERROR`), а при исключении -
`error_type` и `error_message`. Опция `verbose` добавляет состояние портфеля
«было → стало» и оценку сделки. Пароли и хеши (`password`, `salt`,
`hashed_password`, `new_password`) в лог не попадают.

```text
INFO 2026-11-08T23:18:05 REGISTER user='me' result=OK
INFO 2026-11-08T23:18:05 LOGIN user='me' result=OK
INFO 2026-11-08T23:18:05 BUY user='me' currency='BTC' amount=0.0500 rate=59337.21 base='USD' result=OK wallets=[BTC:0.0000->0.0500] estimate=2966.86
INFO 2026-11-08T23:18:05 SELL user='me' currency='BTC' amount=999.0000 result=ERROR error_type=InsufficientFundsError error_message='Недостаточно средств: доступно 0.0500 BTC, требуется 999.0000 BTC'
INFO 2026-11-08T23:18:05 GET_RATE user='me' currency='USD→BTC' rate=0.00001685 result=OK
```

При `log_format = "json"` те же операции выглядят так:

```json
{
  "level": "INFO",
  "time": "2026-11-08T23:19:27",
  "action": "BUY",
  "user": "me",
  "currency": "BTC",
  "amount": "0.0500",
  "rate": "59337.21",
  "base": "USD",
  "result": "OK",
  "wallets": "[BTC:0.0000->0.0500]",
  "estimate": "2966.86"
}
```

Декоратор применён к `register_user` (`REGISTER`), `login_user` (`LOGIN`),
`buy_currency` (`BUY`, `verbose=True`), `sell_currency` (`SELL`, `verbose=True`)
и `get_rate` (`GET_RATE`).

Парсер пишет в свой файл, а не в общий журнал: `parser_logger()` возвращает
отдельный логгер `valutatrade_hub.parser` с `propagate = False` и своим
`RotatingFileHandler` - `logs/parser.log`. Так операции Core и обращения к API
не перемешиваются, а настройки формата, уровня и ротации у обоих журналов
общие (модуль `logging_config` собирается через одну функцию
`configure_logger`). Смотреть журнал парсера - `make parser-logs`
(или `make parser-logs LOG_LINES=50`); подробности - в разделе 4.5.

### 3.5. Бизнес-логика

* `buy`: сессия → `validate_tradable_code` (формат кода, затем реестр валют) →
  `utils.validate_amount` → кошелёк создаётся, если его нет → `deposit` →
  сохранение портфеля через `DATABASE.update` (чтение → изменение → запись) →
  строка лога `@log_action`.
* `sell`: та же проверка кода и суммы → `portfolio.get_wallet` (иначе
  `WalletNotFoundError`) → `withdraw` с проверкой остатка (иначе
  `InsufficientFundsError`, портфель не меняется) → сохранение → лог.
* `get-rate`: формат кодов → реестр (`CurrencyNotFoundError`) → чтение
  локального кеша (`usecases.fresh_rates`): пустой кеш наполняется заглушкой,
  кеш старше `rates_ttl_seconds` даёт `StaleRatesError`, пары нет в кеше -
  `RateLookupError`; обращений в API здесь нет → результат кешируется
  замыканием на время сессии, а `update-rates` сбрасывает этот кеш
  (`usecases.invalidate_rate_cache`), чтобы новые курсы попали в вывод сразу.
* Оценочная стоимость сделки считается по курсу в базовую валюту из
  конфигурации (`base_currency`); строка `Валюта сделки: ...` в выводе CLI
  приходит из `get_display_info()` объекта валюты.

## 4. Сервис парсинга курсов

### 4.1. Цель и архитектура

Parser Service собирает актуальные курсы криптовалют и фиатных валют из двух
публичных API, приводит ответы к единому JSON-формату и сохраняет их локально,
чтобы Core Service работал с кешем `data/rates.json` и не обращался к внешним
сервисам на каждую команду. Разделение даёт четыре полезных свойства:

* бизнес-логика не знает про HTTP: `core/usecases.py` только читает кеш;
* все чужие форматы, таймауты и лимиты заперты в одном пакете
  `valutatrade_hub/parser_service/`;
* у парсера своя история замеров (`data/exchange_rates.json`) и свой журнал
  (`logs/parser.log`), они не мешают Core;
* парсер запускается той же командой `update-rates` и однократно, и фоном по
  расписанию, поэтому его можно вынести в отдельный процесс или cron.

Как текут данные:

```text
CoinGecko ────────────┐
                      ├─> api_clients.fetch_samples()  → [RateSample]
ExchangeRate-API ─────┘                    │
                                           ├─> storage.append_history() → data/exchange_rates.json
                    updater.run_update() ──┤
                                           ├─> storage.write_snapshot() → data/rates.json
                                           └─> logger                   → logs/parser.log

data/rates.json ──> core/usecases (только чтение + TTL) ──> get-rate, buy, sell, show-portfolio
```

| Модуль                | Зона ответственности                                                              |
|-----------------------|-----------------------------------------------------------------------------------|
| `config.py`           | эндпоинты, списки валют, ID-маппинг CoinGecko, пути, таймаут, ключ API из окружения |
| `api_clients.py`      | ABC `BaseApiClient` и два клиента: крипта и фиат; разбор ответов, ошибки API       |
| `storage.py`          | `RatesStorage`: журнал истории и снимок курсов, дедупликация, атомарная запись  |
| `updater.py`          | `RatesUpdater`: опрос клиентов, отказоустойчивость, сводка для CLI, лог каждого шага |
| `scheduler.py`        | `RateScheduler`: фоновый поток с интервалом и корректной остановкой                |

### 4.2. Источники курсов и API-ключ

Два источника выбраны потому, что у каждого сильная своя область: CoinGecko
специализируется на криптовалютах и отдаёт курс сразу по списку монет,
ExchangeRate-API - на фиатных валютах и отдаёт полную таблицу от базовой
валюты одним ответом.

**CoinGecko** - публичный доступ без ключа (для учебных задач его хватает).
Запрашиваются монеты по ID, а не по тикеру:

```text
GET https://api.coingecko.com/api/v3/simple/price?ids=bitcoin,ethereum,solana&vs_currencies=usd

{"bitcoin": {"usd": 75680.0}, "ethereum": {"usd": 2223.93}, "solana": {"usd": 88.94}}
```

Отсюда в проект идут четыре поля: код валюты, курс к базе, отметка времени и
имя источника. Соответствие тикер → ID живёт в `CRYPTO_ID_MAP`, потому что
`SOL` и `solana` - разные сущности:

```python
CRYPTO_ID_MAP = {"BTC": "bitcoin", "ETH": "ethereum", "SOL": "solana"}
```

**ExchangeRate-API** - требует регистрации (бесплатно) и выдаёт персональный
ключ, который вставляется прямо в URL:

```text
GET https://v6.exchangerate-api.com/v6/ВАШ_КЛЮЧ/latest/USD

{
  "result": "success",
  "base_code": "USD",
  "time_last_update_utc": "Sun, 08 Nov 2026 00:00:01 +0000",
  "time_last_update_unix": 1794096001,
  "conversion_rates": {"USD": 1, "EUR": 0.93, "GBP": 0.81, "RUB": 98.4, "TRY": 42.5}
}
```

Здесь `USD` - базовая валюта, от которой посчитаны все остальные курсы.

> Важно: фактический ответ v6 отдаёт таблицу в поле `conversion_rates`, а не в
> `rates`, как в примере задания, и время обновления дублируется в
> `time_last_update_unix`. Клиент принимает оба варианта
> (`RATES_SECTIONS = ("conversion_rates", "rates")`), поэтому работает и с
> реальным API, и с примером из ТЗ.

Бесплатный тариф ограничен количеством запросов в день; при превышении API
отвечает `429 Too Many Requests`. Это не авария приложения: клиент превращает
код в `ApiRequestError` с текстом «превышен лимит запросов (429) - повторите
позже или уменьшите частоту обновления», а `update-rates` продолжает работу со
вторым источником. Частота регулируется интервалом планировщика и таймаутом
запроса.

Ключ нигде не хардкодится: `parser_service/config.py` читает его из переменной
окружения `EXCHANGERATE_API_KEY`. Для локального запуска удобно положить ключ в
`.env` (файл в `.gitignore`) и экспортировать переменные, либо задать их прямо
в команде:

```bash
export EXCHANGERATE_API_KEY="ВАШ_КЛЮЧ"
make run
```

### 4.3. Конфигурация парсера (`parser_service/config.py`)

Все изменяемые параметры собраны в dataclass `ParserConfig`, чтобы логика не
зависела от чисел и строк в коде. Числа и пути берутся из `SettingsLoader`,
поэтому у парсера и Core один каталог данных, одна база расчётов и один TTL.

| Параметр                                | Источник значения                          | Назначение                                     |
|-----------------------------------------|---------------------------------------------|------------------------------------------------|
| `api_key`                               | `EXCHANGERATE_API_KEY` (только окружение)   | ключ провайдера фиатных курсов                 |
| `coingecko_url`, `exchangerate_url`     | константы модуля                             | эндпоинты источников                           |
| `base_currency`                         | `base_currency` (`USD`)                     | база запросов и расчётов курсов                 |
| `fiat_currencies`                       | `("EUR", "GBP", "RUB", "TRY")`              | какие фиатные валюты отслеживать               |
| `crypto_currencies`, `crypto_id_map`    | `("BTC", "ETH", "SOL")`, `CRYPTO_ID_MAP`    | какие крипто и под какими ID их просить         |
| `request_timeout`                       | `parser_request_timeout` (`10`)              | сколько секунд ждать ответ API                 |
| `update_interval_seconds`               | `parser_update_interval_seconds` (`900`)     | период фонового обновления                     |
| `history_limit`                         | `parser_history_limit` (`5000`)              | сколько записей истории хранить                |
| `rates_path`, `history_path`            | `utils.storage_path("rates"/"exchange_rates")` | куда писать снимок и журнал                 |

Правила безопасности и валидности, заложенные в конфиг:

* `ParserConfig.__post_init__` прогоняет все коды валют через общий
  `utils.validate_currency_code` (2-5 заглавных символов), поэтому опечатка в
  списке валют обнаружается на старте, а не в момент запроса;
* `__repr__` и `masked_key()` никогда не отдают ключ целиком: в логи и сообщения
  попадает только маска вида `abcd****wxyz` (или `не задан`);
* `source_name()` нормализует `--source` и даёт подсказку по доступным
  источникам, `has_api_key()` - единственная проверка доступности фиатного
  клиента;
* `from_settings()` перечитывает конфигурацию в момент вызова, поэтому
  `SettingsLoader.reload()` и смена переменной окружения действуют без
  перезапуска процесса.

### 4.4. Два файла парсера: журнал и снимок

**`data/exchange_rates.json`** - «журнал всех измерений». Одна запись = один
уникальный замер пары, с временем получения провайдером и источником. История
нужна, чтобы потом можно было показать динамику и сравнить значения.

```json
[
  {
    "id": "BTC_USD_2026-11-08T21:27:57Z",
    "from_currency": "BTC",
    "to_currency": "USD",
    "rate": 75680.0,
    "timestamp": "2026-11-08T21:27:57Z",
    "source": "CoinGecko",
    "meta": {
      "request_ms": 657,
      "status_code": 200,
      "etag": "W/\"411015ac68b0e7aa2c7e3c3315726c3f\"",
      "raw_id": "bitcoin"
    }
  },
  {
    "id": "TRY_USD_2026-11-08T00:00:01Z",
    "from_currency": "TRY",
    "to_currency": "USD",
    "rate": 0.0199314358606394,
    "timestamp": "2026-11-08T00:00:01Z",
    "source": "ExchangeRate-API",
    "meta": {
      "request_ms": 411,
      "status_code": 200,
      "etag": null,
      "provider_pair": "USD_TRY",
      "provider_rate": 50.172
    }
  }
]
```

Правила записи (реализованы в `RatesStorage`):

* `id = <FROM>_<TO>_<ISO-UTC timestamp>` - детерминированный ключ, поэтому
  повторный опрос того же обновления провайдера не создаёт дубликат:
  `append_history()` возвращает число новых записей (второй прогон подряд даёт
  `0`);
* коды валют в верхнем регистре, 2-5 символов - те же валидаторы, что и у
  кошельков;
* запись происходит только после успешного ответа API и проверки типа данных:
  `RateSample.__post_init__` отбрасывает нечисловые и неположительные курсы;
* запись атомарная: `DatabaseManager.update()` пишет временный файл и делает
  `os.replace`, поэтому в журнале не бывает обрезанного JSON;
* журнал усекается до `parser_history_limit` записей (старые уходят первыми).

**`data/rates.json`** - «снимок текущего мира»: по одному последнему срезу на
пару, именно его читает Core.

```json
{
  "pairs": {
    "BTC_USD": {
      "rate": 75680.0,
      "updated_at": "2026-11-08T21:27:57Z",
      "source": "CoinGecko"
    },
    "EUR_USD": {
      "rate": 1.12,
      "updated_at": "2026-11-08T21:27:58Z",
      "source": "ExchangeRate-API"
    }
  },
  "last_refresh": "2026-11-08T21:27:58Z"
}
```

Правила снимка:

* для каждой пары хранится один последний срез; «побеждает» тот, у кого
  `updated_at` новее (`is_newer`), поэтому опоздавший ответ не переписывает
  свежие данные;
* срок годности (TTL) берётся из `SettingsLoader` (`rates_ttl_seconds`), а не
  зашит в парсер;
* конвенция пары сохранена прежняя: `EUR_USD` = «сколько USD стоит 1 EUR».
  Провайдер считает от базы (`1 USD = 0.93 EUR`), поэтому значение
  переворачивается (`1 / provider_rate`), а сырой курс остаётся в истории
  (`meta.provider_rate`, `meta.provider_pair`) - по нему легко проверить, что
  разбор не перепутал направление;
* два разных момента времени: `timestamp` замера истории - это время
  обновления у провайдера (по нему дедуплицируем), `updated_at` снимка - момент
  нашего опроса (по нему считаем свежесть). Иначе повторный опрос того же
  обновления провайдера выглядел бы как «данные не обновляются».

Core ничего не потерял при смене формата: `utils.load_rates()` нормализует
вложенный `pairs` в плоскую таблицу, а `utils.save_rates()` обратно оборачивает
в формат из ТЗ, поэтому старый плоский `rates.json` тоже читается.

### 4.5. Клиенты API и журнал парсера

Логику каждого источника изолирует свой класс, а единый интерфейс описан в ABC
`BaseApiClient`: потомок реализует только `fetch_samples()`, публичный
`fetch_rates()` со стандартизированным словарём вида
`{"BTC_USD": 59337.21, ...}` определён один раз в базе.

| Элемент                    | Что делает                                                                     |
|------------------------------|--------------------------------------------------------------------------------|
| `BaseApiClient.fetch_rates()` | словарь пар `PAIR -> rate` (ТЗ 4.4.4)                                        |
| `BaseApiClient.fetch_samples()` | абстрактный метод: список `RateSample` из ответа источника                   |
| `BaseApiClient.request_json()` | GET через `requests` с таймаутом; возвращает `(ответ, meta)` - `request_ms`, `status_code`, `etag` |
| `BaseApiClient.check_status()` | коды ошибок превращает в `ApiRequestError` с понятным текстом                |
| `BaseApiClient.available`    | можно ли опросить источник сейчас (фиату нужен ключ API)                       |
| `CoinGeckoClient`            | `ids=bitcoin,ethereum,solana&vs_currencies=usd`, `meta.raw_id` - ID монеты      |
| `ExchangeRateApiClient`      | ключ и база в URL, курсы из `rates`/`conversion_rates`, инверсия к базе        |

Перехват ошибок устроен так, чтобы сеть никогда не «валилась» на Core: любой
`requests.exceptions.RequestException` и любой не-2xx статус - это
`ApiRequestError` с человеческим текстом.

| Ситуация                         | Сообщение исключения                                                          |
|----------------------------------|-------------------------------------------------------------------------------|
| нет связи, DNS, таймаут          | `CoinGecko: сетевая ошибка - <текст requests>`                                |
| ответ не JSON                    | `ExchangeRate-API: ответ не является JSON`                                    |
| `429`                            | `...: превышен лимит запросов (429) - повторите позже или уменьшите частоту обновления` |
| `401`, `403`                     | `...: недоступен ключ API (403) - проверьте переменную EXCHANGERATE_API_KEY`  |
| `404`, иные коды                 | `...: эндпоинт не найден (404)` / `...: сервер ответил кодом 500`             |
| `result != success`, чужая база  | `...: провайдер вернул статус 'error'` / `...: базовая валюта в ответе не EUR` |
| пустой блок курсов               | `...: нет данных ни по одной фиатной валюте`                                  |
| нечисловой или неположительный курс | `ApiRequestError: <источник>: некорректный курс для <PAIR>`               |

Каждый шаг обновления подписывается в отдельный журнал - `logs/parser.log`
(логгер `valutatrade_hub.parser`, `propagate = False`, та же ротация и тот же
формат, что и у основного журнала). Строки операций Core и строки парсера друг
друга не затирают:


### 4.6. Обновление курсов и команды CLI

`RatesUpdater` - точка входа логики парсинга: в конструкторе у него список
клиентов и хранилище, а `run_update(source)` делает четыре шага - опрашивает
каждого клиента, объединяет курсы, добавляет метаданные (`source`,
`last_refresh`) и передаёт результат в `RatesStorage` (сначала история, потом
снимок). Отказоустойчивость встроена в цикл: ошибка одного источника попадает в
`errors` сводки и в журнал, но второй источник всё равно обрабатывается и
пишется в кеш.

Сводка `run_update()` - это то, на чём держится вывод CLI: `total`,
`by_source`, `history_added`, `snapshot_updated`, `errors`, `skipped`,
`last_refresh`, `rates_path`.

#### `update-rates [--source <str>] [--interval <int>]`

Запускает немедленное обновление. `--source` (`coingecko` или `exchangerate`)
ограничивает одним источником, без него опрашиваются оба.

```text
>>> update-rates
INFO: Обновление курсов: старт
INFO: CoinGecko... OK (3 курса)
INFO: ExchangeRate-API... OK (4 курса)
INFO: запись 7 курсов в data/rates.json...
Обновление успешно.
Всего получено курсов: 7, новых в истории: 7. Последний снимок: 2026-11-08T21:27:58Z
```

Строка `INFO: запись ...` печатает полный путь к снимку внутри home запуска
(`VALUTATRADE_HOME` или текущий каталог); в примерах путь сокращён до
`data/rates.json`.

Частичный сбой и недоступный источник - не падение команды:

```text

INFO: Обновление курсов: старт
ERROR: CoinGecko... ошибка: CoinGecko: сетевая ошибка - ...
INFO: ExchangeRate-API... OK (4 курса)
INFO: запись 4 курсов в data/rates.json...
Обновление завершено с замечаниями. Подробности: logs/parser.log
Всего получено курсов: 4, новых в истории: 4. Последний снимок: 2026-11-08T21:31:12Z

>>> update-rates            # без EXCHANGERATE_API_KEY
INFO: Обновление курсов: старт
INFO: CoinGecko... OK (3 курса)
INFO: ExchangeRate-API... пропущен: не задан EXCHANGERATE_API_KEY
INFO: запись 3 курсов в data/rates.json...
Обновление завершено с замечаниями. Подробности: logs/parser.log
Всего получено курсов: 3, новых в истории: 3. Последний снимок: 2026-11-08T21:28:10Z

>>> update-rates --source yahoo
Неизвестный источник 'yahoo'. Доступные: coingecko, exchangerate
```

С `--interval <сек>` обновление уходит в фоновый поток `RateScheduler`, а REPL
остаётся отзывчивым: первый проход выполняется сразу, дальше - по интервалу.
Парсер можно запустить и одним процессом:
`EXCHANGERATE_API_KEY=... python main.py update-rates --interval 900`.

```text
>>> update-rates --interval 4
Планировщик запущен: интервал 4 с, источник: все
Первое обновление выполнено сразу, дальше - по расписанию. Остановка: stop-parser

>>> stop-parser
Фоновое обновление остановлено, выполнено проходов: 7.
>>> stop-parser             # если планировщик не запускался
Фоновое обновление курсов не запущено.
```

Планировщик построен на `threading.Event`: остановка (`stop-parser`, `exit`
или `Ctrl+C` в однократном режиме) не дожидается конца интервала, а сбой одного
прохода не убивает поток - он попадает в `failures` статуса и в журнал.
Нулевой и неположительный интервал отклоняется явно:
`--interval должен быть положительным числом`.

### 4.7. Как Core пользуется кешем

Политика честная и простая: Core читает только `data/rates.json` и никогда не
ходит в API сам.

```python
def fresh_rates():
    rates = utils.load_rates()
    if not utils.pairs_of(rates):          # кеша ещё нет - стартовая заглушка
        return seed_stub_rates()
    if not utils.is_cache_fresh(rates):    # срок годности истёк
        raise StaleRatesError(...)
    return rates
```

* пустой кеш наполняется заглушкой `utils.build_stub_rates` (источник
  `RateServiceStub`) - иначе приложение не даёт зарегистрироваться и купить
  первую валюту до первого `update-rates`;
* кеш старше `rates_ttl_seconds` даёт `StaleRatesError`:
  `Курсы устарели: обновлено 2026-11-08 03:00:00, срок годности 300 с.
  Выполните update-rates.` - и CLI добавляет строку про настройку TTL;
* пары нет в кеше - `RateLookupError` (`Не удалось получить курс для USD→GBP`);
* неизвестная валюта - `CurrencyNotFoundError`, неизвестная база итогов -
  `UnknownCurrencyError`: проверка идёт по реестру валют, а не по кешу, чтобы
  не путать «валюты не существует» и «курса этой валюты пока нет»;
* `update-rates` инвалидирует кеш внутри процесса
  (`usecases.invalidate_rate_cache()`), поэтому новое значение видно сразу в
  `get-rate`, `buy` и `show-portfolio` без перезапуска REPL.

### 4.8. Как это проверялось

Парсер проверяется без сети: клиенты получают подменный транспорт
(`session=`), поэтому разбор ответов, дедупликация истории и отказоустойчивость
воспроизводимы в любой момент. Ниже - сценарии проверки (одноразовый скрипт на
mock-транспорте) и их фактические результаты.

| Проверка на mock-транспорте                                       | Результат                                             |
|--------------------------------------------------------------------|-------------------------------------------------------|
| `fetch_rates()` CoinGecko на примере из ТЗ                          | `{"BTC_USD": 59337.21, "ETH_USD": 3720.0, "SOL_USD": 145.12}` |
| ExchangeRate-API: ответ с `rates` и с `conversion_rates`           | один и тот же набор пар, `EUR_USD = 1/0.927`          |
| `time_last_update_unix` вместо UTC-строки                          | `timestamp` разобран корректно                        |
| повтор тех же замеров в историю                                    | `0` новых записей                                     |
| устаревший замер в снимок / свежий замер                            | `0` / `1` обновлённых пар                             |
| сбой одного клиента (429) при живом втором                         | `total=3`, `errors` из одной записи, кеш обновлён      |
| не задан ключ API                                                    | источник в `skipped`, а не в `errors`                 |
| `RateScheduler(interval_seconds=0)`                                | `ValueError` (реальная ошибка, найденная проверкой)    |
| содержимое `repr`, логов и `rates.json`                            | ключ API не встречается нигде                          |

Живые прогоны (ключ только из переменных окружения, изоляция через
`VALUTATRADE_HOME=$(mktemp -d)`) подтвердили: реальный запрос CoinGecko и
ExchangeRate-API (7 пар в кеше), `update-rates` дважды подряд без дублей в
истории, фоновый режим с `--interval 4` и остановку по `stop-parser`/`Ctrl+C`,
покупку SOL по живому курсу и сводку портфеля в EUR.

Ограничения бесплатных тарифов осознаны: CoinGecko публичный и при частых
запросах отдаёт `429`, ExchangeRate-API ограничен суточным количеством обращений -
поэтому интервал по умолчанию 900 с, а не 60 с, и каждый сбой источника
записывается в `logs/parser.log` вместо молчаливого повтора.

## 5. Демо

Полный цикл показан в записи `demo.cast` (формат asciinema, ~30 с):
`register` → `login` → `buy BTC` → `buy EUR` → `show-portfolio` → `get-rate`,
затем `update-rates` с обоими источниками (7 пар в кеше), `show-rates`,
`show-rates --top 2`, `show-rates --base EUR` и три ветки обработки ошибок:
`InsufficientFundsError`, неизвестная валюта `XYZ` и `help` со таблицей команд.

* **Asciinema**:
```bash
asciinema play demo.cast       
```

Запись сделана реальным прогоном, а не монтажом: приложение запускается в pty,
команды печатаются с паузами, в файл попадает фактический вывод. Данные
репозитория при этом не меняются - запуск идёт с изолированным
`VALUTATRADE_HOME`, а ключ API в запись не попадает: в stdout печатаются только
строки результата (`INFO: ExchangeRate-API... OK (4 курса)`), сам ключ
приходит из переменных окружения и в выводе не участвует (раздел 4.3). После
загрузки на asciinema.org сюда вставляется постоянная ссылка на сессию.
